# CHG-20260812-002 — PAY-MP-002 C3 架构影响与最终代码审核

## Impact Analysis

- CHANGE_ID: CHG-20260812-002
- FEATURE_ID: PAY-MP-002
- Requested Change: 在 PAY-MP-001 之上建立欠费补缴/D1 恢复、基础历史、退款/拒付支持、三方对账、紧急控制和分阶段发布闭环；D-204-B 产品风险参数已批准，进入独立架构与实现门禁。
- Current Architecture: PAY-MP-001 提供 Hosted Mercado Pago Checkout、钱包/直接卡、Invoice/Payment/PaymentOrder、Provider 查询/退款、服务端 D1、Webhook 和 OCPP Start/Stop/MeterValues。当前没有 P002 typed recovery/allocation、chargeback、三方对账、审批、runtime rail 或结构化支持事实。
- Affected Product Domains: App 充电/支付/历史/支持、Billing、Payment、退款/争议、Admin 运营、财务对账、OCPP、权限/租户、审计和发布治理。
- Affected Technical Components: Invoice/Payment/PaymentOrder/Wallet、Checkout/Provider/Webhook、Recovery/Refund/Chargeback/Reconciliation、FinancialEligibility、Charging/OCPP、Support、RBAC/Audit、runtime control、App/Admin projections、PostgreSQL/Outbox。
- Existing Owner Module: Billing owns Invoice/amount; Charging/OCPP owns Session/use/device facts; Payment/Recovery/Reconciliation owns payment/provider/financial recovery facts; Identity owns authorization; Operations owns approvals/control/support. Frontend owns projections only.
- Data Model Impact: C3。需要 additive typed recovery/allocation、refund/approval、chargeback/dispute、reconciliation、rail-control 和 support facts；D-205-A 可先使用查询投影。具体字段/表由后端设计和冻结契约确定，不能使用 metadata/Redis 替代。
- API Impact: `contracts/API.md` 已冻结为 `PAY-MP-002-v1`，覆盖 App bill list/detail/recovery/history/support 与 Admin refund/reconciliation/rail-control 的状态、错误、权限、幂等、分页和兼容；P001 API 含义保持。
- Permission Impact: 当前 payment Admin 为 superadmin-only。目标必须区分 platform/tenant scope、refund request/approve、reconciliation exception approval、rail close/reopen approval、support 和 audit；用户批准的职责分离不可降级。
- Tenant Impact: AppUser D1 为平台级跨运营租户资格；Admin 资源访问从 Invoice/Session/Payment/site 推导 tenant。客户端 tenant_id 不可信。
- Integration Impact: Mercado Pago 继续作为当前 Provider adapter；Provider-specific IDs/payload 留在 adapter/reference 层。OCPP 仍由 Charging/OCPP owner 处理。D-204-B 需经独立架构审核后，才可设计风险 worker 或 RemoteStop 阈值。
- Backward Compatibility: 保留 PAY-MP-001 A1/B1/C1/D1、Hosted boundary、Invoice/Payment/PaymentOrder/Webhook/OCPP 和关闭门禁；P002 新事实 additive，旧 metadata 只作兼容摘要。
- Potential Coupling: High/C3。通过 owner、canonical contract、typed facts、FinancialEligibility 和 Outbox 解耦；禁止 Payment 直接改 OCPP、Frontend 解锁 D1 或 Support 改财务事实。
- Circular Dependency Risk: Payment 状态、D1、OCPP 和 rail-control 若互相直接写表会形成循环；目标架构以事实/服务决定和可靠交接隔离。
- Migration Required: YES for future implementation。无需历史业务导入不代表无需 schema version；本次不创建/执行迁移。必须提供 additive migration、索引、锁/容量、混合版本、校验和 rollback。
- Coupling Level: C3
- Architecture Change Required: YES
- Recommended Integration Strategy: 保留 P001 owner；增加 typed P002 子域和统一 FinancialEligibility；复用 Hosted/Provider adapter/OCPP/Outbox；基础历史使用安全查询投影；运行控制为服务端权威双轴模型。
- Rejected Integration Strategies: metadata/Redis 作为财务 authority；单一 superadmin 完成双控动作；Invoice paid/Provider approved 永久解锁；前端/环境变量当 runtime control；默认 D-204 参数；Provider webhook 直接控制 OCPP；静默切换支付方案或 Provider。
- Reason: 当前代码可以支持 P001 和部分 P0-A 原型，但不能证明已批准的退款、拒付、对账、双控、支持和紧急控制闭环。
- Implementation Dependencies: AR-201～AR-210；共享契约冻结；backend/frontend 设计刷新；独立 QA/E2E。D-204、BE-205 和真实资金发布保持单独 blocked。

## Approved Target Constraints

1. Invoice/Pricing/usage 保持 Billing authority 且不可被 recovery 改写。
2. 钱包、新卡、保存卡统一进入 typed RecoveryAttempt/PaymentAllocation。
3. D1 由唯一 FinancialEligibility evaluator 基于最终财务事实计算，支持 refund/chargeback/reversal/mismatch re-block。
4. D-206-B refund 与 D-207-B exception 使用不同发起/批准人；D-208-B 一人可关闭、不同人员批准恢复。
5. paid charging admission 与 payment creation 是双轴、可作用域、版本化 runtime control；关闭不吞掉收敛流。
6. Mercado Pago 保持 adapter；P002 core contract Provider-neutral。
7. OCPP owner 不变；D-204-B 风险运行时须经独立架构审核和 QA 后才能实现，且不得由 Payment 直接控制 socket。
8. D-205-A 仅基础 App 历史/详情/支付结果；不生成收据文件或 DIAN 发票。
9. D-209-B 使用结构化上下文工单和紧急支持状态，不记录敏感支付数据。
10. 所有跨域状态幂等、可重放、可审计；unknown/mismatch fail closed。
