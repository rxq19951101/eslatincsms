# PAY-MP-002 后端专用产品需求

本文件定义后端必须提供的业务事实、服务端边界和运营能力；不决定 endpoint、数据库表/字段、队列、Provider SDK、锁或部署方式。后续 backend-agent 必须先读取本文件、PRD、ACCEPTANCE、DECISIONS、冻结的 PAY-MP-002-v2 API 和 architecture-agent 结论，再编写技术设计。

## 1. 后端责任

- 维护欠费、补缴、支付、退款、拒付、资金释放、对账、D1 和审计的服务端权威状态。
- 根据已认证 AppUser、Admin 角色、成员关系、账单关联和服务端推导的租户上下文裁决访问，不信任客户端 `tenant_id`、金额、商户或状态。
- 将用户补缴、Provider 回调、主动反查、退款、拒付和资金对账收敛为幂等、可审计的业务事实。
- 在公开收费启动前执行用户明确批准的方案 1及 D-204-B 风险规则：保持 PAY-MP-001 A1、结束后按准确 Invoice 金额扣款并建立风险预算；方案 2 仅保留未来非约束性研究。D-204-B 已完成产品批准，但风险运行时仍须完成架构、契约、实现和 QA 门禁。
- 为 App、Admin、客服、财务和工程提供最小必要的非敏感状态与操作结果；不泄露 Provider 原始 payload 或敏感凭证。
- 提供紧急关闭和恢复的服务端裁决、RBAC、作用域、审计和可验证结果；Admin 只能提交操作意图。

## 2. 业务不变量

### 2.1 欠费、补缴与 D1

- D1 阻断依据是服务端可证明的阻断性未结账单集合；不能由 App 是否显示列表决定。
- 每条未结账单必须能关联原始用户、租户上下文、ChargingSession、Invoice、支付/退款事实和原因类别；原始用量与价格快照不可被补缴覆盖。
- 补缴金额由服务端根据账单当前未结金额裁决；客户端不能修改、超额支付、改变币种或把多账单静默合并。
- 补缴的重复请求、并发点击、重复回跳、Webhook 重放和状态轮询必须幂等；同一账单不能产生重复结算或重复解锁。
- `processing`、unknown、拒绝、退款、拒付或资金未释放不能被判作结清；D1 继续阻断。
- 只有足额结清且没有其他阻断性账单时才能解除 D1；解除后若 Provider 后续事实重新造成风险，必须可重新阻断。
- D1 解锁、重新阻断和人工例外均必须记录审计，包括事实来源和操作者/系统原因。

### 2.2 充电前风险控制

- 后端不能在方案 1 风险预算未完成技术验证、停止动作未验证或风险检查为 unknown 时允许公开收费充电。
- 若用户批准方案 1，才保持 PAY-MP-001 A1：充电结束后按准确 Invoice 金额扣款；用户选择前不得实现或宣称任一未批准的支付语义。
- 方案 1 必须按用户批准的单会话、用户/周期、站点/周期、平台总量、COP/kWh/时间上限和硬停止策略降低最大暴露，并产生可复核风险证据。
- D-204-B 已批准以下参数：单会话 200,000 COP / 100 kWh / 180 分钟；用户未结敞口 250,000 COP；站点周期 1,000,000 COP；平台总量 5,000,000 COP；MeterValues 120 秒降级、300 秒停止；离线/unknown 缓冲 15,000 COP 或 5 分钟；RemoteStop 10 秒内发起并最多自动重试 3 次；StopTransaction 目标 5 分钟；15 分钟自动恢复核查、24 小时最终处理。
- `BE-205` 的方案 1 风险预算执行依赖上述参数完成架构/契约/实现/QA验证；验证前不得进入 production runtime 或真实资金发布。
- 方案 2 的 Provider 预授权/最终捕获是候选研究；不得在用户选择前标记为 `deferred/non-goal`，也不得据此解除产品/架构批准门禁。
- 风险评估结果必须与用户、租户、站点、桩、connector、价格快照和会话关联；不能只依赖 Redis/UI 临时状态。

### 2.3 基础历史、退款、拒付与支持

- 历史查询必须以服务端事实为源，区分会话、Invoice、Payment、Refund、Chargeback 和资金状态。
- 按 D-205-A，P0 只提供服务端基础历史/详情和支付结果投影，不生成 PDF、下载、邮件收据、月结单或 DIAN 电子发票；不得输出 PAN、CVV、证件、Access Token、Refresh Token、原始 Card Token 或 3DS secret。
- 退款累计金额不能超过原批准金额；部分退款、重复退款、Provider unknown 和余额不足必须进入明确状态或异常处理，而非静默成功。
- 按 D-206-B，人工退款必须由一名授权人员提出、另一名授权人员批准；即时产生工单，首次人工响应目标为 1 工作日、决定目标为 3 工作日。
- 拒付/欺诈告警必须能关联原交易和证据截止日期，保留冻结、扣回、返还和责任状态；用户展示只提供可行动的非敏感状态和支持入口。
- 支持查询使用非敏感关联号；后端提供安全的可定位事实，不要求用户提交完整卡号或敏感凭证。

### 2.4 对账、异常和紧急关闭

- 按 D-207-B，每笔支付、退款、拒付和资金释放至少要能在 EsLatin 账务事实、Mercado Pago Provider 事实和实际资金事实间建立可追溯关联，并支持持续匹配与每日关闭。
- 金额、币种、商户、租户、手续费、退款、拒付冻结、资金释放和入账差异必须进入异常状态；未解释差异阻止发布扩展或下一批运营窗口。
- Webhook 验签失败、乱序、重复、主动反查失败、processing 超时和 Provider 不可用不能造成错误 approved、退款或 D1 解锁。
- 前一 Bogotá 营业日须在下一工作日 12:00 前关闭；仅时序/手续费/资金释放差异允许财务与平台批准人接受最长 24 小时的临时例外，其余未解释差异阻止发布扩展。
- 按 D-208-B，紧急控制分别作用于收费充电准入和支付轨，并支持平台/Provider/tenant/site scope；关闭不能删除或破坏进行中会话、Webhook、退款、对账和审计事实。
- 一名授权平台事故人员可关闭；不同授权人员完成健康清单后批准恢复；不自动恢复。支付轨关闭不自动 RemoteStop 活跃会话，D-204 规则另行决定。

## 3. API 与调用方要求

- 具体资源、endpoint、字段、错误码和版本策略统一见已冻结的 [PAY-MP-002-v2 contracts/API.md](../contracts/API.md)；P001 default 与 PAY-MP-002-v1 兼容边界不得破坏。
- App 调用：欠费列表/详情、按账单补缴、补缴状态恢复、基础历史/详情、支付结果、退款状态、上下文支持工单和 D1 可用性结果；不包含 P0 收据文件能力。
- Admin/运营调用：支付/退款/拒付/对账异常检索、人工处理意图、审计查看、支持关联和紧急关闭/恢复意图。
- Provider/后台调用：Webhook 接收、主动反查、退款/拒付/资金报告同步和异常重试；Provider 原始错误只在受控内部日志/审计中保留脱敏版本。
- 所有写操作需要幂等语义；金额、用户、租户、Invoice、支付方式和商户上下文由服务端校验或推导。
- 所有状态查询允许安全重试；未知结果不得通过再次创建支付或再次退款解决。

## 4. 数据和异步链路要求

- 需要评估现有 Invoice、PaymentOrder、Payment、Refund、Chargeback、ChargingSession、Wallet 和 AuditLog 是否足以承载 PAY-MP-002；不预设新增表或迁移。
- 原始 Invoice、价格快照、计量和历史支付事实必须不可变；补缴、退款和拒付通过关联事实表达后续变化。
- Redis、队列、Webhook 或缓存丢失不能伪造已结清、已退款或 D1 解锁；最终状态必须可由持久事实和 Provider 反查恢复。
- 对账和异常处理需要考虑写放大、批次幂等、重放和未解释差异，不恢复无界事件持久化。
- 若需要新增事件、读模型或迁移，必须由 architecture-agent/backend-agent 明确兼容、回滚、空库和历史数据方案后再进入实现。

## 5. 后端验收重点

- 用户/租户/角色隔离和跨租户负例。
- 欠费列表与原始账单事实一致；补缴金额、并发、重复通知、状态未知和 D1 解锁/重新阻断正确。
- 方案 1覆盖硬上限、达到上限安全停止、金额边界、设备异常、unknown/断线和回滚证据；不得把方案 2 研究当作当前验收条件。
- 基础历史/支付结果/退款/拒付事实一致，确认没有误生成收据文件，敏感数据清洗和支持关联安全。
- Provider Webhook 验签、主动反查、乱序/重复/超时、退款幂等和资金对账差异。
- D-206-B 退款双人控制、D-207-B 对账临时例外双人批准、D-208-B 一人关闭/不同人员恢复、审计和进行中会话保护。
- PostgreSQL/Redis 脏数据、孤儿关联、非法状态、重复入账、负钱包余额和金额不一致检查。

## 6. 后端非范围

- App/Admin 页面、导航、组件、i18n、视觉和本地交互实现。
- 任何具体 endpoint、数据库表/字段、迁移、ORM、队列、锁、Provider SDK 或部署决定。
- guest、PSE、Nequi、现金、分期和 C2 租户分账。
- D-205-B/C 的 PDF/下载/邮件收据和 DIAN 电子发票。
- 实现方案 1 风险控制；D-204-B 技术验证完成前不得进入生产运行。方案 2 不属于当前实现范围。
- 生产部署、生产密钥、`PAYMENT_RAILS_ENABLED` 修改和真实生产操作。

## 7. 后续架构审核问题

- 这是对现有支付/账单/运营域的扩展，还是需要建立欠费恢复、对账异常和支付风险子域？如何避免循环依赖？
- D1 的权威解锁条件、重新阻断条件和人工例外是否需要新的领域状态或事件？
- 现有 PaymentOrder/Invoice 是否能表达“原账单 + 补缴尝试 + 退款/拒付后续事实”，以及如何做到不可重复？
- 选定路线与当前 Hosted Checkout、`charging_direct` Token 生命周期、保存卡 CVV、3DS 和 A1 的兼容性如何证明？
- 选定路线的风险上限存储、并发计数、设备停止和跨实例一致性由什么事实源负责，且如何只消费用户批准的参数？
- Admin 紧急关闭、对账和拒付权限是否跨租户，需不需要平台级安全边界或双人审批？
- 需要哪些 API/事件/数据库变化，是否需要迁移，如何回滚并保证已有 PAY-MP-001 用户和历史支付可继续查询？

## 8. 当前首个垂直切片与任务门禁

- 在架构审核、契约冻结和实现授权完成后，首个可实现垂直切片建议为 `BE-201/BE-202/BE-203`：不可变账单事实 → 按账单补缴 → 服务端状态恢复 → D1 解锁/重新阻断。
- 对应的 `FE-201/FE-202/FE-203` 负责 App 欠费查看、账单目标与补缴入口、处理中恢复和服务端 D1 recheck；本文件不替代前端需求。
- `BE-205` 已达到 `contract-frozen / implementation-ready-for-BE205`，可按 D-204-B v2 contract 进入实现计划；在 runtime、独立 QA/E2E、容量和发布门禁完成前不得启用计数器或硬停止。
- `BE-204` 只允许记录方案 2 的非约束性可行性研究，不得在用户选择前标记为 `deferred/non-goal`，也不形成实现依赖。
- 以上是产品实现优先级，不解除当前 C3 architecture/contract/QA/生产门禁。
