# PAY-MP-002 前端专用产品需求

本文件定义 App 与 Admin 的用户体验和展示责任；不冻结 API 字段、状态枚举、导航路径、组件、数据存储或技术实现。后续 frontend-agent 必须根据已冻结的 PAY-MP-002-v2（并保持 P001/v1 compatibility）实现，不得以 UI 逻辑替代后端账务、权限或 D1 事实。

## 1. 前端责任

### App

- 提供 D1 阻断后的欠费列表、账单详情、按账单补缴、处理中恢复和结清后重新充电入口。
- 按 D-205-A 提供基础充电历史/详情、支付结果、退款状态解释和支持入口；不提供 PDF/下载/邮件收据或 DIAN 发票。
- 展示已批准方案 1 的充电后按准确 Invoice 扣款说明、价格/估算和后续 D-204 上限触发反馈；D-204 未批准前不得展示虚构数值。
- 只提交用户意图，调用后端安全 Checkout/补缴/查询能力；不计算最终金额、不修改状态、不解除 D1。

### Admin

- 提供按角色和租户范围的支付、退款、拒付、对账异常、支持关联、审计和支付轨状态工作台。
- 支持运营提交退款、人工处理、备注、升级、对账确认和紧急关闭/恢复意图；显示后端返回的成功/失败/需审批状态。
- 显示受保护的非敏感 Provider/EsLatin 参考号和异常原因类别，不渲染原始 Provider payload 或支付密钥。

## 2. App 页面与用户流程

### 2.1 D1 阻断与欠费列表

- 用户在扫码/开始充电被阻止时看到：阻断原因、可查看欠费入口、支持入口和安全重试；不出现无操作出口的错误页。
- 欠费列表优先展示仍阻断充电的账单；每项至少展示站点、设备/connector、时间、用量（若可用）、未结金额、原因和状态。
- 账单详情展示原始充电事实、价格快照、未结原因、当前应补金额和可用补缴方式；不显示未冻结字段或客户端猜测。
- 补缴按钮只能以服务端返回的账单为目标；客户端不允许编辑金额或将多笔账单合并成不可解释的支付。
- 支持新卡、保存卡 CVV、钱包等服务端允许的方式；支付完成后回到账单详情并重新拉取服务端状态。
- `processing/unknown` 显示处理中和“不要重复支付”；失败/拒绝显示可行动重试或支持；结清后显示可继续充电，但仅以服务端 D1 解锁结果为准。
- 若还有其他阻断账单，单笔结清后继续显示阻断和剩余账单；不能以单笔成功乐观解锁全部。

### 2.2 公开收费充电与资金风险说明

- 开始前展示站点、桩/connector、价格、估算/上限、支付方式及用户批准路线对应的文案。
- 方案 1 已获得方向性批准，可展示无预授权/冻结/预扣/最终捕获、待批准上限/停止规则和 A1 结束后扣款风险；具体上限必须等待 D-204。方案 2 获批后必须按其批准的 Provider 语义展示。
- 用户批准前，方案 1/方案 2 文案都只能作为非约束性设计输入，不进入上线验收。
- 任何风险模型未就绪、资金检查未知或后端安全阻止时，显示不可启动和支持入口，不允许前端绕过。
- 充电达到上限、设备异常、网络中断、3DS/Provider 状态未知时，给出不会重复支付/启动的恢复动作。

### 2.3 基础历史、退款和支持

- App 具有基础“充电历史”入口，可按记录进入详情；至少区分充电完成、已支付、未支付、处理中、已退款、部分退款、争议/拒付。
- 详情展示站点、设备/connector、起止时间、kWh、价格快照、COP 金额、支付方式非敏感摘要、状态和支持入口。
- 按 D-205-A，不设计独立收据页面、PDF、下载、邮件发送、月结单或 DIAN 发票入口；支付结果与非敏感参考号显示在基础详情内。
- processing、unpaid、refund pending、disputed 不得显示“支付成功/已结清”主状态；必须提供刷新、补缴、查看退款或支持入口。
- 按 D-206-B/D-209-B，从 D1、账单、支付、退款、拒付和充电详情建立结构化支持工单，只携带非敏感关联号和问题类别；显示工单及退款状态和 1/3 工作日目标，不要求用户填写完整卡号、CVV、证件号或 Provider token。
- 公开收费站点在公布营业时段显示实时紧急支持入口；没有值守渠道时不能呈现该站点可收费启动。
- 无记录、数据加载失败、网络断开、权限不足、已删除/不可见记录分别显示明确状态，不用 demo 数据遮盖。

## 3. Admin 工作台要求

- 支付运营能够按非敏感用户/账单/订单/会话/Provider 参考号检索，并查看状态时间线、异常类别、重试/反查结果、退款/拒付状态和支持关联。
- 按 D-207-B，财务查看持续匹配、每日三方对账、手续费、退款、拒付冻结/扣回、资金释放/入账差异；显示次工作日 12:00 Bogotá 关闭时限和最长 24 小时双人批准临时例外。
- 运营能够查看待处理退款、拒付证据截止、Webhook/Provider 异常、D1 恢复失败和设备已交付但支付失败的队列。
- 具备权限的角色可以提交退款/人工处理/紧急关闭/恢复意图；退款显示一人提出/另一人批准，关闭显示一人可关闭/不同人员恢复，页面显示确认、范围、原因、审批状态、审计参考和最终服务端结果。
- 普通租户管理员只能看到本租户允许的运营事实，不能查看平台其他租户、全局资金、Provider secret 或平台级紧急关闭细节。
- D-208-B 紧急控制 UI 分开显示“收费充电准入”和“支付轨”，并明确停止新增入口与进行中会话继续收敛的区别；恢复前展示当前 scope、负责人、健康清单和不同人员审批信息，不提供自动恢复。
- Admin 不直接写环境变量、不直接调用 Provider、不直接修改数据库状态；若后端拒绝或状态未知，页面显示待处理/支持路径。

## 4. 状态、语言和可访问性

- App/Admin 都覆盖 loading、empty、ready、processing、unknown、declined、unpaid、refunding、refunded、disputed、permission denied、offline、retry 和 terminal 状态。
- 西班牙语（es-CO）是 P0 首要语言；支付、退款、拒付、对账和 D1 文案不得使用 Provider 原始错误或内部编码。
- 金额按 COP locale 展示，保留服务端精度语义；时间按用户 locale 展示，服务端事实为 UTC。
- 列表/详情/按钮/表格在窄屏、桌面和触摸场景可用；颜色不是唯一状态表达，焦点、键盘、screen reader、错误播报和 loading disabled 状态可用。
- 退款/关闭/人工处理等危险操作需要明确确认、不可逆/影响范围提示和结果反馈；重复点击不会重复提交。
- App 不在 Redux、AsyncStorage、日志、截图上报或错误追踪中保存 PAN、CVV、证件号、Access Token、原始 Card Token 或 3DS secret。

## 5. API 依赖

- 资源、字段、错误和状态仅引用已冻结的 [PAY-MP-002-v2 API](../contracts/API.md)；前端不得自行发明字段或路径。
- App 依赖：D1/欠费列表与详情、账单补缴、支付状态恢复、历史、收据、退款状态、支持入口和风险检查结果。
- Admin 依赖：异常队列、对账状态、退款/拒付处理意图、审计时间线、支付轨状态和紧急关闭/恢复意图。
- 所有最终成功/失败/解锁状态来自服务端；Deep Link、Provider 页面回跳和本地缓存只作为恢复触发。
- 前端不提交 `tenant_id`、最终账单金额、商户账号、Provider secret 或权限结论。

## 5.1 当前首个垂直切片与任务门禁

- 在架构审核、契约冻结和实现授权完成后，首个可实现垂直切片建议为 `FE-201/FE-202/FE-203`：欠费查看 → 按账单补缴 → 状态恢复 → D1 解锁，对应后端为 `BE-201/BE-202/BE-203`。
- `FE-203` 的成功态必须等待服务端足额结清和 D1 recheck；本地回跳、按钮结果或单一通知不得解锁。
- `FE-204` 只能展示用户明确批准且由 `BE-205` 提供的路线/风险说明；未批准前只能形成交互模型。
- `BE-204` 的方案 2 预授权/最终捕获是候选研究，不能在用户选择前标记为 `deferred/non-goal`。
- 以上是产品优先级建议，不解除当前 C3 architecture/contract/QA/生产门禁。

## 6. 前端验收重点

- D1 阻断→查看欠费→按账单补缴→处理中/失败→结清→服务端解锁→重新充电的完整 App 旅程。
- 多账单、重复点击、网络中断、后台恢复、过期、权限不足、无记录、账单不可见和跨租户负例。
- 用户批准方案 1 后，用户披露才可包含无预授权的结束后扣款、已批准阈值、达到上限安全停止和状态未知；方案 2 获批后按其 Provider 语义验收，未批准方案不进入验收。
- 基础充电历史/详情、支付结果、退款/拒付状态、支持入口和状态时间线；验证不存在未批准的收据下载/邮件/DIAN 入口。
- Admin 异常/对账/退款/拒付/审计/紧急关闭工作台的角色和租户边界。
- i18n、响应式、键盘/焦点、screen reader、危险操作确认、共享组件和相邻钱包/充电回归。

## 7. 前端非范围

- 后端支付、D1、账务、Provider、Webhook、退款记账、拒付证据、对账、OCPP 或紧急关闭实现。
- 具体 endpoint、公共类型、数据缓存、导航结构、组件和状态管理方案。
- 在 App/Admin 内实现 Provider 卡表单、预授权/冻结/预扣/最终捕获算法、风险计数器或权限裁决；风险预算只由后端服务端裁决。
- guest、PSE、Nequi、现金、分期和 C2 租户分账。
- D-205-B/C 的独立收据页面、PDF/下载/邮件发送和 DIAN 电子发票。
- 业务代码、API 实现、数据库、迁移、部署或生产配置修改。

## 8. 后续架构/前端设计问题

- App 欠费列表与历史是否复用现有导航/Payment Hub，还是需要新的跨域入口？如何避免 D1 状态与本地缓存不一致？
- 账单补缴与现有 `charging_direct`/saved-card/wallet flow 的页面复用边界是什么，如何保证原账单目标不可被用户或深链篡改？
- D-205-A 的基础详情需要冻结哪些安全字段，如何保证没有收据文档依赖？
- Admin 支付运营、财务、支持和工程是否共享工作台，还是分角色视图；如何分别呈现退款双人控制、对账临时例外双人批准和不同人员恢复？
- 紧急关闭的 UI 仅显示状态还是允许提交意图；如何确保恢复由后端授权而不是前端开关？
- 哪些 App/Admin 共享状态需要统一本地化映射，如何在 API 演进和 unknown 状态下保持安全回退？
- 方案 1/方案 2 的研究结果如何在用户明确选择后重新走产品/架构门禁？
