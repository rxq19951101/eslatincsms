# PAY-MP-002 验收标准

以下验收标准定义公开上线最低产品闭环。它们不冻结 endpoint、数据库字段、Provider SDK 或技术状态名；后续实现必须映射到服务端权威事实并由独立 QA/E2E 验证。

## 1. 发布前置与优先级

1. **P0-A** 欠费列表、账单详情、按账单补缴、处理中/失败恢复和 D1 解锁全部可用；只完成阻断提示不算通过。
2. **P0-B** 用户已明确选择方案 1（保持 A1 + 量化风险预算），因此可按准确 Invoice 扣款方向进行产品验收；但 COP/用量/时间/停止条件和损失上限仍受 D-204 门禁约束。方案 2 仍未选择，若未来纳入必须先完成 Provider 预授权/捕获能力与用户流程的独立批准。D-204 或技术证据不足时不得公开上线。
3. **P0-C** 按 D-205-A，App 可查看基础充电历史/详情及支付结果，不生成下载/邮件收据或 DIAN 发票；按 D-206-B/D-209-B 提供退款状态、结构化支持工单及站点紧急支持。
4. **P0-D** 支付、退款、拒付、对账、审计、监控和紧急关闭形成可演练的生产闭环。
5. PAY-MP-001 的生产最低要求、QA、E2E、人工和法律/财税/商业门禁仍然适用；PAY-MP-002 不能单独把 PAY-MP-001 的 NO-GO 改成 GO。

## 2. 欠费自助查看与补缴

1. Given 用户因 D1 被阻止开始收费充电，When 用户点击查看欠费，Then App 显示所有当前阻断性未结账单或明确的安全错误/支持入口，不显示空白死路。
2. Given 欠费列表有多条账单，When 用户进入列表，Then 每条账单能区分站点、桩/connector、充电时间、用量、价格快照、未结金额、原因类别和当前状态；排序/分页需由后续契约明确且保持稳定。
3. Given 用户打开一条账单，When 查看详情，Then 补缴金额以服务端当前未结金额为准，用户不能自由修改、超额支付或静默合并账单。
4. Given 账单允许补缴，When 用户选择新卡、保存卡或钱包并确认，Then 补缴关联原账单，不改变原充电用量、价格快照或历史支付事实。
5. Given 支付方式不可用，When 用户尝试补缴，Then 系统说明不可用原因类别，提供可行的其他方式或支持入口，不创建假成功。
6. Given 用户重复点击、刷新、重复回跳或收到重复通知，When 同一账单正在补缴，Then 最多形成一个可解释的有效结算事实，不重复扣款、不重复入账、不重复解锁。
7. Given 补缴处于 processing/unknown，When 用户查看结果，Then D1 继续阻断，页面明确“处理中/不要重复支付”，支持安全刷新或稍后返回。
8. Given 补缴失败或拒绝，When 状态收敛，Then D1 继续阻断，用户可重试或联系客服，原账单保持未结。
9. Given 补缴最终被服务端确认足额结清且没有其他阻断性账单，When 用户刷新或重新进入充电，Then D1 解除；解锁事实可跨页面、重登和换设备恢复。
10. Given 退款、拒付或后续 Provider 事实让已结清账单重新有风险，When 服务端重新评估，Then D1 可重新阻断并向用户提供原因与支持入口。
11. Given 用户不属于该账单或租户，When 请求查看/补缴，Then 不泄露账单存在性，不允许操作。

## 3. 充电开始前资金风险

1. Given 用户已批准某一产品路线，When 用户查看公开收费确认页，Then 页面展示价格/估算、对应扣款规则、支付方式和已批准的资金风险说明。
2. Given 用户明确批准了方案 1，When 用户开始充电，Then 产品按 A1 在结束后以准确 Invoice 金额扣款；页面不得宣称或要求预授权、冻结、预扣或最终捕获。
3. Given 用户明确批准方案 1且具体风险预算参数已批准，When 用户开始充电，Then 服务端按批准的单会话、用户/周期、站点/周期、平台总量、用量/金额和时间上限裁决，并在达到阈值时安全停止或禁止继续。
4. Given 用户尚未批准路线，或选定路线的数值、停止条件、恢复 SLA 或验证证据不足，When 用户尝试开始充电，Then 系统安全阻止并提供支持/重试，不允许无边界后付。未批准方案不属于本阶段验收门。
5. Given 设备离线、RemoteStart 失败、网络中断、3DS 超时或 Provider 状态未知，When 充电/支付状态未确定，Then 不把支付验证显示为最终付款，不重复启动或重复扣款，并提供恢复入口。
6. Given 会话达到批准的风险上限，When 系统执行停止/限制，Then 保留完整充电和风险审计事实，并能生成最终账单或人工处理任务。
7. 若用户选择方案 1，其最大单次损失、用户周期损失、站点周期损失、平台总损失、触发时间和恢复时间均有明确用户批准和可验证证据；具体 COP、kWh、时间和范围数值未批准前不得填写为已批准事实。

### 3.1 当前首个垂直切片门禁

1. 架构审核和 draft contract 冻结后，首个可实现垂直切片建议严格为 `BE-201/BE-202/BE-203 + FE-201/FE-202/FE-203`：欠费查看 → 按账单补缴 → 状态恢复 → D1 解锁。
2. 方案 1 已获方向性批准，但 `BE-205` 的风险预算执行依赖 D-204 的具体数值审批；在审批前只能形成建模/设计输入，不能把任何 COP、kWh、时间或范围值当作实现参数。
3. `BE-204` 仅保留 Mercado Pago 方案 2 的候选可行性研究；在用户选择前不得标记为 `deferred/non-goal`，也不解除欠费恢复垂直切片的产品批准门禁。
4. “首个垂直切片”是产品优先级建议，不解除当前 C3 架构、契约、实现、QA 或生产门禁。

## 4. 基础历史和支付结果（D-205-A）

1. Given 用户打开历史，When 查看记录，Then 能区分充电会话、Invoice、支付、退款和拒付，并按服务端状态显示，不把设备启动等同支付成功。
2. Given 一笔充电已产生账单，When 打开详情，Then 显示站点、桩/connector、起止时间、kWh、价格快照、税/费用/优惠（如适用）、COP 最终金额、支付方式非敏感尾号和状态。
3. Given 状态为 processing/unpaid/refund pending/disputed，When 用户查看，Then 页面明确不是最终结清或仍有风险，并提供刷新/支持/补缴等可行动入口。
4. Given 用户查看一笔记录，When 需要支付证据，Then App 展示服务端支付结果和非敏感参考号；P0 不提供独立收据文件、PDF、下载、邮件发送或 DIAN 电子发票。
5. Given 用户在不同设备或稍后返回，When 查看历史，Then 历史和支付结果由服务端恢复，不依赖本地临时 UI 状态。
6. Given 用户没有任何记录，When 打开历史，Then 显示明确空状态和帮助入口，不伪造示例交易。

## 5. 退款状态与用户支持

1. Given 用户从支付/账单详情进入退款，When 查看状态，Then 至少能区分申请中、处理中、已完成、部分退款、失败/需人工和拒付/争议。
2. Given 部分退款发生，When 用户查看收据，Then 原金额、已退金额、剩余实收和状态清晰，累计退款不超过已支付金额。
3. Given 退款或 Provider 状态未知，When 系统重试/回查，Then 不重复退款、不重复记账，用户看到处理中/需支持而非假成功。
4. Given 用户点击支持，When 创建或进入支持请求，Then 自动携带非敏感业务参考号、问题类别和当前状态；不要求完整卡号、CVV、证件号或密钥。
5. Given 发生重复扣款、支付成功但账单未结清、无法结束充电、金额异常、退款延迟或拒付，When 用户联系客服，Then 入口可达、话术可行动、支持人员可按参考号定位并留下处理记录。
6. 西班牙语为首要用户语言；关键状态、按钮、错误、帮助和基础历史字段覆盖 loading、空、处理中、失败、成功、退款和 D1 阻断。
7. Given 退款需要人工执行，When 提交 Provider 退款，Then 一名授权人员提出、另一名授权人员批准；任何一人不能独立完成同一笔人工退款。
8. Given 工单已创建，When 用户查看，Then 即时获得参考号；首次人工响应目标为 1 工作日、决定目标为 3 工作日，Provider/银行入账时间另行展示。
9. Given 用户遇到无法停止/拔枪或安全问题，When 站点处于公布收费营业时段，Then 可访问实时紧急支持渠道；没有值守渠道时站点不能在该时段开放收费。

## 6. 运营、对账和审计

1. Given 一笔 Provider 支付/退款/拒付/资金释放事实，When 运营或财务对账，Then 能映射到 EsLatin 用户、租户上下文、ChargingSession、Invoice、Order/Payment、Refund/Chargeback 和审计事实。
2. Given Webhook 重复、乱序、签名失败、主动反查超时或 Provider processing，When 系统处理，Then 状态最终可收敛或进入明确异常队列，不重复入账、退款或解锁。
3. Given 金额、币种、商户、租户、手续费、退款或资金入账不一致，When 对账发现，Then 标记为阻断级差异，阻止相关发布/扩大窗口，并分配负责人和处理时限。
4. Given 财务完成日对账，When 关闭对账批次，Then 前一 Bogotá 营业日在下一工作日 12:00 前完成；未解释金额差异为零，或时序/手续费/释放差异由财务与平台批准人记录最长 24 小时的临时接受；仅日志存在不算通过。
5. Given 支付运营处理退款、拒付、人工恢复或配置操作，When 操作完成，Then 记录操作者、角色/范围、原因、目标、原状态、新状态、Provider 参考号和结果。
6. Given 需要紧急关闭，When 具备授权的运营/工程人员执行，Then 新的收费支付/启动入口停止；进行中会话、回调、退款和对账仍可收敛；关闭/恢复/验证均有审计。
7. Given 普通租户管理员没有平台级权限，When 尝试处理跨租户支付、拒付或紧急关闭，Then 后端拒绝并不泄露其他租户事实。
8. 运营工作台、App 和后台接口的错误/状态均来自同一服务端事实，不能通过手工修改前端或 Admin 展示绕过账务或 D1。
9. Given 发生紧急关闭，When 授权事故人员操作，Then 可分别按范围停止收费充电准入或支付轨；一人可关闭，不同人员批准恢复，不自动恢复，且支付关闭不自动强停活跃会话。

## 7. 非功能、回归与发布门禁

1. 金额采用十进制定点语义；时间以 UTC 存储并按用户 locale 展示。
2. 支付、补缴、退款、拒付、Webhook、紧急关闭和 D1 解锁均需幂等、可重试、可审计。
3. App/Admin 不接触 Provider secret、PAN、CVV、证件号、原始 Card Token 或 3DS secret。
4. 必须验证多租户、用户隔离、角色权限、历史不可变性、脏数据、孤儿支付、重复账单和状态乱序。
5. 后端 QA、前端 QA 和 E2E 必须分别提供独立证据；未知 Provider/数据库/设备状态不能判定 PASS。
6. 发布采用 D-210-B：R0 沙盒、R1 生产暗启动、R2 内部真实支付、R3 封闭测试、R4 人工公开上线；每级均需独立 QA/E2E 和 Product Owner 明确晋级，本文不授权部署或启用支付轨。
7. R2 限 1 个批准站点、2 台试点桩、最多 10 名用户、至少 20 个完成收费会话和连续 7 天；R3 最多 50 名用户、至少 100 个完成收费会话和连续 14 天。
8. 重复/超额扣款、跨租户访问、无法解释的资金差异、支付成功但无可追溯 Invoice、无法关闭新增风险、Webhook 验签失败或紧急支持不可用均为晋级阻断。
