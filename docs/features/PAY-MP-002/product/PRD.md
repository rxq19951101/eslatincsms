# PAY-MP-002 公开上线支付闭环

## 1. 问题与目标

PAY-MP-001 已建立 Mercado Pago 托管支付、钱包/银行卡结算、D1 服务端欠费门禁、退款和基础对账能力，但尚未形成公开上线所需的“出错后可恢复、资金风险可量化、用户可举证、运营可处置”的闭环：

- 用户被 D1 阻止后，当前没有按账单查看、补缴和事实解锁的完整自助旅程。
- A1 是充电结束后按准确金额扣款，存在已交付电量但最终付款失败的敞口。用户已批准保持 A1 并增加量化风险预算/硬停止；Provider 预授权/最终捕获仍是未批准候选路线。
- 用户需要查看充电、账单、支付和退款的历史证据，并能快速进入支持入口。
- 支付运营、财务和工程需要逐笔对账、异常队列、审计证据和紧急关闭能力，而不是只依赖 Provider 回调或日志。

目标是补齐哥伦比亚公开上线的 P0 产品闭环，同时保留 PAY-MP-001 已批准的 A1/B1/C1/D1、D-008 和 D-017。用户已明确批准 D-203 方案 1、D-204-B 以及 D-205-A、D-206-B、D-207-B、D-208-B、D-209-B、D-210-B，并确认整体产品基线。D-204-B 现进入独立架构审核、契约、实现和 QA 门禁；在这些门禁完成前不得开放真实资金收费。

## 2. 成功标准

以下是产品验收目标，不是当前已达成的运行数据：

- 每一条阻断 D1 的未结清账单都能被当前用户查看、定位到原充电事实，并呈现可行动的全额补缴入口或明确的支持入口；不得出现只有“无法充电”而没有原因和恢复路径的死路。
- 补缴只有在服务端确认最终结清后才解除 D1；客户端回跳、单次按钮结果或单个 Webhook 不能单独解锁。
- 当前公开上线资金风险路线已确定为方案 1，但具体量化风险预算、硬上限、达到上限安全停止和欠费自助恢复仍需批准；在参数、架构、实现和验证均未完成前不得 GO。
- 充电、Invoice、Payment、Refund、Chargeback 和资金对账事实可以按非敏感参考号相互追溯；金额、币种、商户和租户不一致为阻断级异常。
- 用户可以看到基础充电历史/详情、支付和退款状态并从同一上下文进入支持；P0 不提供可下载/邮件收据或 DIAN 发票；客服不要求完整卡号、CVV、证件号或 Provider 密钥。
- 支付、退款、拒付和紧急关闭操作具有可审计的操作者、时间、原因、范围和结果；支付轨可以被服务端紧急关闭并验证新收费入口不再接受。

## 3. 用户、角色与责任边界

| 角色 | 目标 | PAY-MP-002 产品责任 |
|---|---|---|
| App 车主 | 继续充电、补缴、查看基础记录/支付结果和求助 | 提供查看/操作入口和状态反馈，不裁决账务或 D1 解锁事实 |
| 支付/客服运营 | 定位用户账单、补缴失败、退款、拒付和支持工单 | 处理异常、人工协助、退款/争议流程并保留证据 |
| 财务 | 核对 Provider、EsLatin 和实际资金 | 逐笔/批次对账、差异处理、手续费/退款/冻结/入账核对 |
| 工程值班 | 保障支付、Webhook、OCPP/账务链路 | 监控、告警、异常处置、紧急关闭和恢复验证 |
| Admin 租户/平台管理员 | 在授权范围内查看和操作运营数据 | 提供受 RBAC 和租户范围约束的运营意图；不能绕过后端状态机 |
| 法律/财税/商业负责人 | 确认 C1 收款主体和消费者承诺 | 确认退款、拒付、税务凭证、支持 SLA、数据处理和租户责任 |

### 3.1 App/Admin/Backend 边界

- App：展示服务端返回的欠费、基础历史/详情、支付结果、退款和支持状态；提交用户选择；支持安全重试、回跳恢复和本地化。不生成 P0 收据文件，不保存或计算最终账务，不自行解除 D1。
- Admin：提供支付运营、财务和支持工作台；展示待处理异常、对账差异、退款/拒付证据和支付轨状态。Admin 只能提交操作意图，后端负责权限、租户、状态、幂等和审计裁决。
- Backend：拥有账单/支付/退款/拒付/对账/D1/审计事实，负责 Provider 反查、异步收敛、权限隔离、紧急关闭和恢复。前端不能直接访问 Provider、数据库或生产密钥。

## 4. P0 范围

### P0-A：欠费自助查看、补缴与 D1 恢复

- 展示当前用户所有仍阻断收费充电的账单，至少能识别原充电站点、充电桩/connector、时间、用量、价格快照、未结金额、原因类别和当前状态。
- 支持用户选择一条账单进入详情，并以该账单当前未结金额为补缴金额；禁止客户端自由改价、超额支付或把多条账单静默合并成不可解释的一笔。
- 支持补缴方式：新卡、已保存卡（重新采集 CVV）或钱包余额；D-202 已获批准，但可用方式仍由服务端根据账单、用户、支付状态和 Provider 能力返回。
- 一条账单可重复安全尝试，但同一账单的并行点击、重复回跳、Webhook 重放和刷新不能重复结算或重复解除门禁。
- 补缴处理中时，用户看到“正在确认，不要重复支付”，D1 仍保持阻断；失败/拒绝时保持阻断并允许安全重试或联系客服。
- 只有服务端确认该账单已足额结清且没有其他阻断性未结账单后，才解除 D1。解锁状态必须能在重新登录、刷新、换设备后恢复。
- 退款、拒付、撤销或后续 Provider 事实使已结清账单重新产生风险时，系统必须重新评估 D1 并明确通知用户；不能永久信任历史“已支付”展示。
- 补缴不能修改原 Invoice 的充电用量、价格快照、原支付事实或审计历史；补缴是对原未结账单的结清关联。

### P0-B：充电开始前资金风险控制

#### 当前产品方向与参数审批

用户已明确批准方案 1（保持 PAY-MP-001 A1）：充电结束后按准确 Invoice 金额扣款，并通过 D-204-B 量化风险预算控制敞口。方案 2（Mercado Pago 预授权/冻结/预扣/最终捕获）仍只是未批准候选，不得进入当前实现路线。

方案 1 的 D-204-B 参数已获产品批准；以下参数仍必须经过架构、契约、实现和 QA 验证：

| 参数 | 必须批准的内容 | 当前状态 |
|---|---|---|
| 单会话金额上限 | 200,000 COP；达到后采取安全停止 | 产品已批准，待架构/QA验证 |
| 单会话能量上限 | 100 kWh；与金额上限冲突时采用更严格者 | 产品已批准，待架构/QA验证 |
| 单会话时长上限 | 180 分钟；与其他上限冲突时采用更严格者 | 产品已批准，待架构/QA验证 |
| 用户未结敞口 | 250,000 COP；达到后禁止新付费会话 | 产品已批准，待架构/QA验证 |
| 站点周期敞口 | 1,000,000 COP；与平台使用同一 UTC 滚动 24 小时窗口，无午夜重置；active/unresolved 计入 | 产品已批准，待架构/QA验证 |
| 平台总敞口 | 5,000,000 COP；同一 UTC 滚动 24 小时窗口；已释放/已结算不计入 | 产品已批准，待架构/QA验证 |

| 欠费恢复 SLA | 15 分钟内自动核查，24 小时内最终处理；常规路径不要求人工介入 | 产品已批准，待架构/QA验证 |

方案 1 不是“默认无风险”。只有上述参数完成技术实现、停止动作验证、审计证据、欠费自助恢复和运营演练后，才能进入公开上线评估。

#### 共同产品要求

- 用户在开始前看到最终扣款规则、价格/估算和用户批准路线的风险预算/硬上限说明；文案不得暗示未批准的支付语义。
- 方案 1 的充电启动资格必须包含后续批准的风险预算结果；结果由服务端裁决，前端不能绕过。
- 风险预算参数获得批准后，充电期间监控实际用量和累计金额；达到批准的上限时必须安全停止、提示用户并形成账单/支持事实。
- 充电开始失败、用户取消、设备离线、网络中断、3DS 超时、Provider processing 和最终 Invoice 不一致都必须有明确恢复路径。
- 方案 1 必须可量化地说明：最大单次损失、最大用户周期损失、最大站点周期损失、平台总损失、触发停止时间和未结账单恢复时间。
- 未完成风险预算数值审批、架构审核、后端/前端实现、QA、E2E 和运营演练前，公开发布保持 NO-GO。

- 前端：`FE-201`、`FE-202`、`FE-203`。

- 方案 1 风险预算执行相关的 `BE-205` 已获得 D-204-B 产品输入，但必须先完成架构审核、契约更新、实现和独立 QA；门禁完成前只能形成建模/设计输入。
- `BE-204` 保留 Mercado Pago 方案 2 的候选预授权/最终捕获研究；用户选择前不属于当前实现路线，也不构成非目标或批准。

### P0-C：基础历史、退款与支持

- 按 D-205-A，App 提供基础充电历史列表和详情，展示站点/设备、时间、kWh、价格快照、COP 最终金额、支付结果、退款/争议影响和支持入口；不能把“已启动充电”显示成“已付款”。
- P0 不提供独立收据文件、PDF、下载、邮件发送、月结单或 DIAN 电子发票。后续增加这些能力必须重新经过产品决策。
- 按 D-206-B，用户可从相关详情提交结构化问题/退款请求；退款由两名不同授权人员提交和批准，支持全额/部分退款，返回原支付方式，累计退款不超过实付金额。
- 退款状态至少区分已收到、审核中、已批准、Provider 处理中、部分退款、已退款、已拒绝和需人工；即时返回工单，首次人工响应目标为 1 工作日，决定目标为 3 工作日。
- 按 D-209-B，支持入口从 D1、账单、支付、退款、拒付和充电详情进入，携带非敏感关联号和问题类别；App 提供工单状态，邮件用于通知，客服不能改写财务事实。
- 公开收费站点必须在其公布营业时段提供实时紧急支持渠道；无法提供 24/7 支持时，只能在有值守的公布时段开放收费。
- App 支持西班牙语为首要语言，并覆盖 loading、空、离线、处理中、失败、重试、已结清、已退款和被 D1 阻断状态。

### P0-D：生产运营闭环

- 逐笔关联 EsLatin 的 User/ChargingSession/Invoice/Order/Payment/Refund/Chargeback/Audit 与 Mercado Pago Provider/payment/refund/dispute/fee/settlement 事实。
- 每笔支付和退款必须有最终状态收敛机制；Webhook、主动反查、重试、乱序和重复通知不能造成重复入账、重复退款或错误解锁。
- 支付异常至少覆盖：Provider 拒绝、processing 超时、金额/币种/商户/租户不一致、Webhook 验签失败、重复批准、退款未知、资金未释放、拒付/欺诈告警、设备已交付但支付失败。
- 按 D-207-B，Admin 提供持续逐笔匹配和每日三方对账的异常检索、处理、备注、升级及 CSV 导出；前一 Bogotá 营业日须在下一工作日 12:00 前关闭。金额/币种/商户/租户、重复扣款和无法解释的资金差异阻止下一阶段发布。
- 仅时序、手续费或资金释放差异可以进入最长 24 小时的临时风险接受，且需要财务批准人和平台批准人、负责人及到期时间；到期未解决重新阻断。
- 按 D-208-B，紧急控制分别作用于收费充电准入和支付轨，可按平台/Provider/tenant/site 范围关闭；关闭不停止 Webhook、主动查询、退款、对账、历史和支持。
- 一名授权平台事故人员可关闭；不同授权人员完成健康清单后批准恢复；不自动恢复。支付紧急关闭不自动强停活跃会话，D-204 风险停止规则另行决定。
- 普通租户管理员不能操作平台/Provider 紧急控制；关闭、恢复和验证均须审计。

## 5. 用户流程

### 5.1 D1 阻断到解锁

1. 用户扫码或开始收费充电时，服务端发现一条或多条阻断性未结账单，返回安全阻断状态。
2. App 显示阻断原因、未结账单数量/总额（仅服务端确认可展示时）和“查看并补缴”入口，同时提供支持入口；不显示可疑或未冻结的金额字段。
3. 用户进入账单列表，选择一条账单查看原充电和未结原因。
4. 用户选择可用补缴方式并完成安全 Checkout/钱包支付；补缴金额固定为该账单的服务端未结金额。
5. App 显示处理中并从服务端恢复状态。批准且足额结清后，用户可刷新或返回充电流程；若还有其他阻断账单，继续显示阻断。
6. 账单失败、退款、拒付或状态未知时，D1 不解锁；用户看到下一步和支持入口。

### 5.2 公开收费充电

1. 用户查看站点、connector、价格、支付方式和资金风险说明。
2. 服务端根据已批准风险模型判断是否允许进入充电启动。
3. 用户明确确认后启动；充电用量和累计金额可见，达到风险上限时安全停止。
4. 结束后生成最终 Invoice，支付状态通过 Provider/服务端事实收敛。
5. App 展示最终账单/支付结果或明确的 processing/unpaid/refund 状态，并能从详情进入支持；D-205-A 不提供收据文件。

### 5.3 退款/拒付/支持

1. 用户从历史详情选择“退款状态/报告问题/联系客服”。
2. App 建立上下文工单并展示状态和非敏感关联号；支持系统按关联号定位，不要求敏感支付数据。
3. 一名运营/财务人员提出退款，另一名授权人员批准；Provider 事实变化通过服务端回写，用户看到状态更新，不以客服手工文字替代账务事实。

## 6. 业务不变量

- D1 是服务端事实门禁；任何 UI 乐观状态、回跳或单个通知都不能解锁。
- 补缴不得改变原充电计量、价格快照或历史账单金额；不得通过负钱包余额隐藏欠费。
- 资金金额使用 COP 十进制定点语义；任何 UI 展示与 Provider/Invoice 金额不一致都属于异常。
- Provider 支付、退款、拒付和资金释放状态必须按正确状态迁移收敛；未知状态不能判定成功。
- 用户、账单、支付历史和支持数据按当前用户及服务端推导租户隔离；Admin 不能通过客户端参数越权。
- 关键操作和紧急关闭必须记录操作者、授权范围、时间、原因、目标、旧状态和结果。
- PAN、CVV、证件号、Access Token、Refresh Token、原始 Card Token 和 3DS secret 不进入 App、普通 API、日志或用户支持内容。

## 7. P1 与明确非范围

P1（不阻塞第一版公开上线闭环，除非负责人提升优先级）：

- 高级历史筛选、导出和运营报表自助化。
- 可下载/PDF/邮件商业收据、月结单和 DIAN 电子发票；任何一个进入开发前都需要新的产品及财税/法律批准。
- 用户自助发起复杂争议/拒付举证表单；P0 仍必须有支持入口和运营内部处理能力。
- 多渠道消息通知的扩展（短信、WhatsApp 等）；P0 先保证 App/Admin/客服入口和关键状态可达。

明确非范围：

- guest/免账户支付。
- PSE、Nequi、现金、分期或其他新增支付轨。
- C2 租户 OAuth、Split Payments、平台抽佣、租户分账和租户独立收款。
- 自动订阅、自动续费、车队月结或无 CVV 静默代扣。
- D-205-B/C 的收据文件、邮件发送和 DIAN 电子发票。
- 在本需求中直接决定 Mercado Pago 预授权/最终捕获的 endpoint、数据库字段、Provider SDK 用法或技术替代方案。
