# PAY-MP-001 哥伦比亚生产上线最低要求

## 1. 文档目的与效力

本文定义现有 Mercado Pago 支付模块进入哥伦比亚生产环境前必须具备的最低产品闭环、运营证据和 Go/No-Go 门禁。本文不证明任何门禁已经通过，也不授权部署、启用真实支付或修改生产状态。

本文不推翻以下已批准决定：

- A1：充电结束后按实际账单金额扣款。
- B1：使用 EsLatin 托管的 Mercado Pago 安全结账页。
- C1：首期由 EsLatin 平台商户统一收款。
- D1：存在任何欠费时阻止下一次充电。
- D-008：本期欠费列表、银行卡/钱包补缴 UI 和欠费恢复页延期。
- D-017：P0 不实现也不宣称预授权、冻结或预扣。

当这些决定与不同发布等级的最低风险闭环发生冲突时，本文只记录 `proposed` 决策和安全边界，必须由项目负责人批准后才能改变产品事实。

竞品事实与推导依据见 [COMPETITOR_BENCHMARK.md](./COMPETITOR_BENCHMARK.md)。

## 2. 当前结论

截至 2026-08-12：

- **预金丝雀准备：NO-GO。** 后端 QA 当前由负责人暂停，已有独立报告结论为 `blocked`，不存在 PASS；独立前端 QA 已于 2026-08-12 执行，自动化、构建和静态审查已运行，但整体结论为 `blocked`，仍缺真实后端、Provider、设备、3DS 和可访问性证据；E2E 为 `not-started`。此外仍缺完整 Mercado Pago sandbox/退款、支持值班、事故演练及法律/财税/隐私签字。
- **单笔生产金丝雀：未授权。** 只有预金丝雀门禁全部通过并取得一次性书面人工批准后，才能在指定窗口由一名内部测试人员执行最多一笔低额生产支付。
- **受控试点扩展：NO-GO。** 单笔金丝雀完成后，还必须先关闭支付轨、逐笔三方对账，并使用该笔生产 Payment ID 完成 Mercado Pago 生产质量评估，证据通过后才能另行审批扩大试点。
- **公开发布：NO-GO。** 除上述共同缺口外，当前“无预授权 + 充电后扣款 + 欠费无自助补缴入口”会同时产生电量敞口和用户锁死风险，需要负责人批准公开发布风险方案。
- `PAYMENT_RAILS_ENABLED` 的默认和窗口外有效值必须为 `false`。现有前端 QA 报告记录的生产配置有效值风险尚未关闭；本文不修改配置，也不授权部署或启用真实支付。

## 3. 发布等级

### 3.1 预金丝雀准备门禁（Pre-canary Readiness）

预金丝雀门禁在不产生真实生产扣款的前提下确认系统、人员和风险边界已可安全执行一次生产验证。最低要求为：

- 独立 Backend QA 和 Frontend QA 均为 PASS；现有 `paused-by-owner` 或 `blocked` 不能视为通过。
- 在测试/sandbox 环境完成 App→Checkout→Provider→Webhook→OCPP/结算→收据/退款→数据事实的 E2E，并取得 PASS。
- 新卡、保存卡、信用/借记/预付卡、3DS、拒绝、processing、网络未知、Webhook 验签/重试/乱序、全额/部分退款均有适用的真实 Mercado Pago sandbox 或 Provider 证据。
- 生产形态 HTTPS、监控告警、紧急关闭、回滚、支持值班、财务对账、事件响应和法律/隐私/财税/商业检查均已演练或签字。
- 金丝雀计划已写明内部测试人、唯一支付用途、金额上限、站点/connector（如适用）、精确起止时间、值班人、停止条件、退款安排和证据负责人。
- 人工审查只批准“一名内部测试人、一个窗口、最多一个生产 Payment ID”，不自动批准受控试点或公开发布。
- 审批时及金丝雀窗口开始前，必须由授权操作人证明 `PAYMENT_RAILS_ENABLED` 的有效值为 `false`。

**非门禁项：** 单笔生产支付本身和 Mercado Pago 基于生产 Payment ID 的质量评估不属于预金丝雀证据，否则会形成“未获准生产就必须先生产”的循环门禁。预金丝雀只要求相关操作方案、权限、监控和证据模板准备完毕。

### 3.2 单笔生产金丝雀（One-payment Production Canary）

预金丝雀获得 GO 后，仍需负责人对具体金丝雀窗口作书面批准。该窗口必须满足：

- 只有一名已列名内部测试人员可以操作，且最多创建一个生产 Payment ID；支付用途必须预先选定，不得在窗口中扩展为多个旅程。
- 如选择 `charging_direct`，批准书必须同时列明站点、充电桩、connector、最大电量/COP 敞口和设备停止负责人；如选择确定金额旅程，也必须列明金额和退款安排。
- 授权操作人只可在所有预检完成、测试人员准备点击支付之前，将 `PAYMENT_RAILS_ENABLED` 的**有效运行值**临时设为 `true`；不得提前开启等待，也不得借此开放其他用户、站点或支付目的。
- 取得唯一生产 Payment ID、触发任何停止条件或到达批准窗口结束时间三者中任一项后，授权操作人必须立即把有效运行值恢复为 `false`，并验证新生产支付无法再创建。即使该笔支付仍为 `processing`，支付轨也必须先关闭，既有回调和主动反查继续收敛该笔事实。
- 窗口外、服务重启后和任何未明确批准的环境中，有效值必须保持 `false`；再次启用需要新的书面金丝雀批准。
- 本文只定义产品门禁和操作时序，**不授权部署、修改生产配置、接触生产密钥或执行该金丝雀**。

### 3.3 金丝雀后核对与质量评估（Post-canary Review）

支付轨恢复为 `false` 后，必须先完成：

- 将唯一 Payment ID 映射到 EsLatin 用户、业务目的、订单/会话、Invoice、Payment、租户及 Mercado Pago 最终事实。
- 对 EsLatin、Mercado Pago 和实际资金账户执行逐笔三方核对；任何 processing 未收敛或金额、币种、商户、租户、退款、手续费差异未解释时保持 NO-GO。
- 使用该生产 Payment ID 运行 Mercado Pago 生产集成质量评估，保存评分、问题和整改证据；测试报告或空资金报告不能替代此步骤。
- 按批准方案验证收据、支持查询、监控告警和必要的退款/取消；记录窗口启闭、停止条件和复盘结论。

只有上述证据均通过，负责人才能对下一阶段“受控试点扩展”作独立审批。金丝雀成功不自动批准扩展。

### 3.4 受控试点（Controlled Pilot）

受控试点是单笔金丝雀及其核对/质量评估通过后的有限扩展，不等于公开上线。最低边界为：

- 仅邀请制且可实名联系的用户，不开放自然流量注册后直接支付。
- 仅开放负责人明确列出的站点、充电桩、时段和运营人员。
- 每用户、每会话、每日及全试点累计 COP 风险上限必须在启动前以具体数字批准。
- 必须有可立即关闭支付入口和停止新增收费会话的操作负责人。
- 支付支持和账务人员在整个试点时段在线；试点结束当日完成逐笔对账。
- D-008 可以暂时保留，但只有在支持人员能够定位欠费、协助用户完成合法补缴或人工解除错误门禁，并留下审计证据时才允许试点。
- 每个获批试点窗口开始前才允许按运行手册临时开启支付轨；窗口外或达到停止条件后立即关闭，不能把金丝雀批准沿用为长期启用授权。
- 任一资金不一致、重复扣款、无法退款、无法解释的欠费或跨租户暴露都立即停止试点。

### 3.5 公开发布（Public Launch）

公开发布面向非邀请用户并允许持续收费。除受控试点门禁外，最低要求为：

- 用户不依赖人工客服即可查看未结清账单、理解原因、选择可用方式补缴，并在事实结清后恢复充电资格。
- 必须批准并实现公开发布的充电前资金风险控制。首选评估预授权/最终捕获；如继续无预授权，则必须有经负责人批准、可量化且经架构审查的等效风险方案。
- 提供稳定的账单/收据历史、退款状态、支持入口和争议处理说明。
- 客服、支付运营、财务对账和工程值班具备非试点时段的持续覆盖。
- 法律、财税、隐私和商业负责人对 C1 收款主体、消费者条款、退款、拒付、税务凭证及租户结算责任书面签字。

## 4. 支持的支付旅程与发布边界

| 旅程 | 已批准产品形态 | 受控试点最低要求 | 公开发布最低要求 |
|---|---|---|---|
| 新卡单次收费充电 | `charging_direct`，不保存卡，结束后按准确金额扣款 | 可纳入，但必须受邀请名单和金额敞口上限约束 | 需要已批准的充电前风险控制和自助欠费恢复 |
| 已保存卡收费充电 | 独立绑卡；每次重新采集 CVV | 可纳入，须验证保存、删除、默认卡、CVV、3DS 和最终扣款 | 同试点要求，并具备支付方式失效后的更新与恢复入口 |
| 钱包充值 | 金额确定后支付，Provider 批准才入账 | 必须证明重复通知不重复入账、失败不入账、退款不形成负余额 | 还需持续对账、历史收据和异常工单闭环 |
| 钱包收费充电 | 会话结束后余额足额才扣款 | 余额不足不得错误结清；须显示明确结果 | 需要余额不足后的可行动恢复，不得只显示死路错误 |
| 免费充电 | 0 COP 审计事实，无 Provider 扣款 | 验证无 Provider 交易和无钱包流水 | 同左；不得被展示为缺失价格 |
| 欠费补缴 | 服务端能力保留，App UI 延期 | 只允许支持主导的有限恢复，并必须逐笔审计 | **硬门禁：必须交付用户自助列表、补缴和门禁解除闭环** |
| 全额/部分退款 | 银行卡原路退；累计不超过已支付金额 | 必须在真实 Provider 环境完成至少一次可核对退款 | 必须有用户状态、运营入口、SLA、对账和重复请求保护 |
| 访客/免账户支付 | 不在当前范围 | 不开放 | 不属于首期公开发布最低范围；若新增需另立产品与风险评审 |
| PSE、Nequi、现金、分期 | 不在当前范围 | 不开放 | 不阻塞首期卡支付发布；新增需单独需求 |

## 5. 支付状态与恢复体验

### 5.1 总体规则

- App 回跳、Deep Link、前端页面或 Webhook 单一事件都不能单独宣告支付成功；用户展示必须以服务端已核验的支付事实为准。
- 所有处理中状态必须告诉用户“不要重复支付”、当前会发生什么、何时自动更新以及如何主动刷新/求助。
- 所有失败状态必须区分“未扣款或未确认”“可能仍在处理中”“已产生欠费”“退款处理中”，禁止统一显示模糊失败。
- 用户关闭 App、网络中断、3DS 返回失败或 Webhook 延迟不能丢失当前订单和恢复入口。
- 任何错误都不得要求用户向客服提供完整卡号、CVV、证件号码、Card Token、Access Token 或验证码。

### 5.2 最低状态矩阵

| 产品状态 | 用户必须看到 | 允许的用户动作 | 运营/恢复要求 |
|---|---|---|---|
| Checkout 未创建/暂不可用 | 当前无法安全打开支付，不代表扣款 | 重试、返回充电页、联系支持 | 记录失败率和 Provider/平台原因，不创建假订单 |
| Checkout 过期/缺失 | 会话已失效，卡表单不可继续使用 | 返回并重新创建 | 旧引用不得被重新确认或自动启动充电 |
| 卡验证失败/拒绝 | 未通过验证；给出可行动但不泄露 Provider 内部码的原因类别 | 检查资料、换卡、稍后重试 | 统计拒绝类别，避免无限重试和撞库 |
| `action_required` / 3DS | 银行需要额外验证并给出剩余操作 | 完成验证、返回 App、放弃 | 仅打开受信任 URL；超时后主动核验最终事实 |
| Payment Intent `ready` | 银行卡已验证，但尚未扣款，充电也尚未开始 | 用户明确点击启动 | 禁止把验证成功表达为已付款 |
| 设备启动失败 | 充电未开始，未产生最终充电账单 | 重试同一安全意图或更换设备 | 不得创建重复收费；保留可审计失败事实 |
| 充电进行中 | 当前用量、价格规则和预计/累计金额（若可靠） | 停止充电、查看帮助 | 支付验证与设备会话必须可关联但状态独立 |
| `processing` | 最终金额已提交，结果仍在确认 | 等待、刷新、稍后查看 | 轮询、Webhook、主动反查最终收敛；禁止重复提交 |
| `approved` | 最终用量、金额、支付方式尾号和收据入口 | 查看/下载收据、报告问题 | Invoice、Payment、Order、Session 和 Provider 金额一致 |
| `declined/error/expired/unpaid` | 最终账单未结清、当前不能继续充电及下一步 | 试点联系支持；公开版立即补缴 | D1 继续生效；不得把失败写成已支付 |
| `refunding` | 退款申请已受理、金额、原支付方式和预计处理说明 | 查看状态、联系支持 | 与 Provider 状态和累计退款额对账 |
| `partially_refunded/refunded` | 原金额、已退金额、剩余实收和处理日期 | 下载更新后的凭证 | 累计退款不得超过原支付金额 |
| `charged_back/disputed` | 不把内部争议证据暴露给普通用户；提供支持渠道 | 联系支持 | 支付运营按截止日期提交证据并跟踪资金结果 |

Mercado Pago 官方资料显示，3DS Challenge 期间支付会保持 pending，用户通常只有约 5 分钟完成验证；超时可能被拒绝。因此 3DS 超时、返回 App 和最终状态反查都属于硬门禁。[Mercado Pago 3DS](https://www.mercadopago.com.co/developers/en/docs/checkout-api-payments/how-tos/integrate-3ds)

## 6. 定价、扣款和收据披露

### 6.1 开始充电前

用户在最终确认前至少看到：

- 站点、充电桩、connector 和运营方名称。
- `paid | free | unavailable` 的明确含义；无价格不得默认为免费。
- COP 计价单位、费率、适用时段、税费、停车/占位费或其他可能收费项。
- 价格快照在本次会话中的生效规则；开始后调价不得追溯覆盖。
- A1 文案：“充电结束后按实际账单金额扣款”。
- 当前 P0 **不进行预授权或资金冻结**；不得使用“已授权额度”“已预扣”“已付款”等表述。
- 单次新卡不会保存；保存卡需要独立操作；保存卡付款仍会要求 CVV。
- C1 下用户付款的收款/账单主体为 EsLatin；最终对账单显示名称须由商业与法律负责人确认。
- 证件类型/号码仅在 Mercado Pago 安全边界内用于卡 Token 化，EsLatin 不保存。

### 6.2 充电结束后

可查看或下载的收据至少包含：

- 收据/账单编号、会话编号和可供支持查询的非敏感支付参考号。
- 站点、充电桩、connector、开始/结束时间和时区。
- 充电量（kWh）、计价快照、费用组成、税费、优惠、退款调整和 COP 最终总额。
- 支付方式类型、品牌和尾号；不得显示完整 PAN、CVV、证件或原始 Provider Token。
- 支付状态、支付/退款时间、收款主体、对账单描述和支持联系方式。
- 如处于 processing、unpaid 或 refund pending，凭证必须明确是临时状态而不是最终结清证明。

## 7. 欺诈与资金敞口控制

### 7.1 受控试点硬要求

| 控制 | 最低要求 | 当前状态 |
|---|---|---|
| 用户范围 | 邀请名单、可联系用户、禁止匿名和批量注册滥用 | 待负责人给出名单与准入规则 |
| 单会话敞口 | 以 COP 明确最大可交付电量/金额；达到上限时有安全停止策略 | 待负责人决策 |
| 用户/日敞口 | 以 COP 和会话数定义上限，跨站点累计 | 待负责人决策 |
| 全试点敞口 | 以 COP 定义总风险预算；达到阈值停止新增收费会话 | 待负责人决策 |
| 支付尝试频率 | 限制同用户、卡指纹/Provider 事实、设备和网络来源的高频失败 | 待 QA 证据 |
| 3DS | Provider 要求时完整执行，不允许前端绕过 | 待真实 sandbox/Provider 证据 |
| D1 | 任意欠费立即阻止新会话，错误解除必须审计 | 已有开发事实；待独立 QA/E2E |
| 紧急关闭 | 支付运营可以立即停止新支付，不破坏进行中会话与账务事实 | 待运行手册与演练 |
| 重复扣款 | 同一业务目的只接受一个成功事实；重复成功进入退款/异常队列 | 已有开发事实；待 Provider 验证 |

### 7.2 公开发布额外硬要求

- 负责人必须在以下两条路径中批准一条，并触发必要的 C3 产品/架构评审：
  1. 在充电前完成可支持最终准确金额结算的预授权/捕获方案；或
  2. 保留无预授权 A1，但提供经量化证明的等效控制，包括低敞口上限、异常实时停止、风险分层和完整自助欠费恢复。
- 未批准路径前，公开发布保持 NO-GO；受控试点通过不能自动升级为公开发布。
- 任何白名单、金额上限或人工例外都必须由服务端事实裁决并形成审计，不能依赖 App 隐藏按钮。

## 8. 取消、退款和争议

### 8.1 取消与未开始会话

- 用户在最终支付批准前放弃支付，按 Provider 能力取消 pending/in-process，不宣称发生退款。
- 设备未成功启动且未交付电量时，不创建最终充电费用；若 Provider 已出现资金事实，必须主动核验并取消/退款。
- 充电已开始后，停止充电只结束用量，不等同于取消已交付电量的账单。

Mercado Pago 区分取消和退款：未批准的 pending/in-process 支付可取消；已支付交易通过全额或部分退款返还。官方当前说明退款通常可在批准后 180 天内发起，且商户账户需要足够可用余额。[Mercado Pago 取消与退款](https://www.mercadopago.com.co/developers/es/docs/checkout-api-payments/payment-management/cancellations-and-refunds)

### 8.2 退款最低规则

- 支持错误扣款、重复扣款、设备未交付电量、运营补偿等明确原因码。
- 直接卡支付原路退回；钱包充值退款不得造成负钱包余额。
- 支持全额和部分退款；累计退款不超过原批准金额。
- 用户看到申请金额、已退金额、剩余实收、状态和预计处理说明。
- Provider 超时、未知状态或回调丢失时不得重复退款；必须先反查。
- 每次退款都关联原 Invoice、Payment、会话、操作者、原因和 Provider 事实。

### 8.3 拒付与争议最低规则

- 启用并监控 chargeback/fraud alert 通知；收到后立即建立工单并记录证据截止日期。
- 证据包至少能关联用户、会话、站点、桩、时间、计量、价格快照、用户确认、支付和支持记录。
- 由支付运营审核是否需要提交证据；法律/商业负责人确认争议策略和可接受损失。
- 争议资金不能当作已安全结算资金；财务对账单独标识冻结、败诉扣款和胜诉返还。

Mercado Pago 官方说明，拒付会冻结争议金额，可能要求商户在期限内提交资料，最终资金可能被扣回；官方还建议使用清晰账单描述和详细付款凭证降低“不认识交易”的争议。[Mercado Pago chargeback](https://www.mercadopago.com.co/developers/en/docs/checkout-pro/chargebacks)

## 9. 客服与运营准备

上线前必须完成以下责任分配，不允许只写团队名称而没有当班人员和联系方式：

| 职责 | 最低能力 | 必需证据 |
|---|---|---|
| L1 西语客服 | 查询非敏感订单、解释 processing/declined/unpaid/hold/退款、建立工单 | 西语话术、支持入口、排班和升级矩阵 |
| 支付运营 | Provider 反查、重复扣款、欠费、退款、Webhook、拒付处理 | 运行手册、最小权限账号、审计样例 |
| 财务 | 日对账、资金释放、手续费、退款、争议和银行入账核对 | 对账模板、签字人、差异清单 |
| 工程值班 | 支付、App、OCPP、Redis、数据库和 Webhook 事故定位 | 监控面板、告警路由、回滚/关闭演练 |
| 事件负责人 | 判断停止试点/支付、用户通知和恢复 | 事件等级、联系人和演练记录 |
| 法律/隐私/商业 | 条款、隐私、收款主体、税务凭证、退款和租户结算责任 | 书面签字或风险接受记录 |

最低客服原则：

- App 的支付结果、订单/收据页面和站点帮助入口均能找到支持渠道。
- 客服可以用订单号定位，不要求用户提供完整卡号或敏感凭证。
- 重复扣款、无法结束充电、金额明显异常、支付成功但账单未结清属于最高支付优先级。
- 支持工单必须关联支付/会话事实并记录处理结果，不能仅在聊天工具中结案。

## 10. 对账与财务证据

### 10.1 三方核对

生产支付至少执行以下三方核对：

1. EsLatin：ChargingSession、Invoice、PaymentOrder、Payment、Wallet/Refund 审计事实。
2. Mercado Pago：Payment、Refund、Chargeback、费用、资金冻结/释放和通知事实。
3. 资金账户：Mercado Pago 可用/释放资金报告、提现/银行入账及 C1 下后续租户应结算金额。

Mercado Pago 官方把集成质量评估列为生产准备能力；其中生产质量测量需要一个生产 Payment ID。EsLatin 应在预金丝雀阶段准备评估与证据模板，但只能在获批的单笔生产金丝雀生成 Payment ID 后执行实际生产质量测量。测试账户的资金释放报告可能没有真实数据，因此 sandbox 测试不能替代金丝雀后的逐笔生产对账。[生产要求](https://www.mercadopago.com.co/developers/en/docs/checkout-api-payments/integration-test/go-to-production-requirements) · [资金释放报告](https://www.mercadopago.com.co/developers/en/docs/reports/released-money/introduction)

### 10.2 单笔生产金丝雀证据标准

- 只有预先批准的一名内部测试人员、一个支付目的和最多一个生产 Payment ID。
- `PAYMENT_RAILS_ENABLED` 的启用、关闭和关闭后失败关闭验证均有时间、操作者和有效值证据；窗口外保持 `false`。
- 该 Payment ID 能唯一映射到 EsLatin 业务事实，并在 Provider 和资金账户中完成逐笔核对。
- 使用该 Payment ID 完成 Mercado Pago 生产集成质量评估，并保存结果；任何未解决问题都阻止试点扩展。
- `processing` 可以在支付轨关闭后继续由 Webhook/主动反查收敛，但在最终事实和对账清楚前不得扩大生产范围。

### 10.3 受控试点证据标准

- 100% Provider 交易能够映射到唯一 EsLatin 业务目的、用户、会话/充值和租户。
- 100% EsLatin approved/refunded/charged-back 资金状态能够找到对应 Provider 事实。
- Invoice、Provider 支付、退款和实际入账金额之间不存在未解释差额。
- 每日由支付运营制表、财务复核签字；未解释差异未清零前不得开始下一试点批次。
- 手续费、税、退款、争议冻结和资金释放不得与用户应付金额混为同一列。

### 10.4 公开发布额外要求

- 有固定频率的自动或半自动对账、差异告警、责任人和处理时限。
- 能重放对账而不重复入账、退款或改变已冻结历史金额。
- 月末可追溯 C1 平台收款到各租户运营交易和应结算金额；C2 未启用前不得把 Provider 分账当作已存在。

## 12. 可观测性最低要求

上线面板和告警至少覆盖：

- Checkout 创建、打开、确认和过期数量及成功率。
- 新卡/保存卡、信用/借记/预付卡和 3DS 各路径结果。
- Payment Intent 创建、消费、设备启动失败和 Token 丢失/过期。
- Provider `processing/action_required/approved/declined/error/expired` 数量与停留时长。
- Webhook 验签失败、重试、重复、乱序、处理延迟和主动反查失败。
- Invoice 与 Provider 金额/币种/商户/租户不一致。
- 欠费用户数、欠费 COP、单笔/用户/站点敞口和 D1 阻断次数。
- 退款申请、成功、未知、超时、累计金额异常和重复 approved 异常。
- Chargeback/fraud alert、证据截止日期和争议资金。
- 对账差异、资金释放延迟、Provider/API 可用性及紧急关闭状态。

每项必须有负责人批准的阈值、告警接收人、处置手册和恢复确认；仅有日志而无可行动告警不算通过。

### 立即 No-Go 条件

- 支付、退款、钱包或欠费存在金额不一致、重复入账、跨用户或跨租户访问。

- 支付轨在未获批窗口、窗口开始前、取得唯一 Payment ID 后或窗口结束后仍保持开启。
